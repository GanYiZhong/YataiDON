# iOS 首屏前启动等待修复日志

日期：2026-09-13。

## 现象与定位

用户报告点开 App 后，游戏画面出现前约等待 1600ms。iPhone 18 Pro / iOS 27.0 模拟器、Release 构建复现了首屏前的明显等待，但绝对耗时比用户真机更长。

`main()` 在创建窗口前调用 `ios_prepare_filesystem()`，遍历内置 GameData（本次构建共 13,522 个文件），将缺失资源补到 Documents。即使资源已经存在，每次启动仍然：

1. 对每个条目调用 `std::filesystem::relative()`，解析源路径和资源根目录的真实路径，重复访问祖先目录。
2. 为每个文件再次调用 `create_directories()` 检查父目录。
3. 对已有的非着色器文件调用 `copy_file(skip_existing)`，再由复制函数检查是否跳过。

模拟器分段计时显示，文件系统准备约占重复启动初始化时间的 86%–88%，是本次确认的主要瓶颈。网络探测阶段不到 1ms；此次使用未配置服务器的离线构建，不能据此判断在线构建的启动耗时。

## 修复

仅修改 `src/platform/ios.mm`：

- 迭代器已经给出以资源目录为根的路径，改用 `lexically_relative()` 计算相对路径，避免逐文件解析真实路径。
- 目录遍历先访问父目录，移除每个文件重复的父目录创建检查。
- 已存在的非着色器文件直接跳过复制；着色器仍随每次启动覆盖更新。

仍遍历资源树以补齐缺失文件，不引入“初始化完成”标记。首次复制、用户配置和皮肤保留、新增内置资源补齐、缺失子目录修复等行为保留。其他平台的代码未修改。

## 测量结果与验证

同一模拟器、同一资源集，资源已存在，终止应用进程后重新启动。下表列出各版本两次重复启动的阶段耗时范围（不是累计值）：

| 阶段 | 修复前 | 修复后 |
| --- | ---: | ---: |
| Documents 资源准备 | 3543–3628ms | 249–252ms |
| 配置与成绩数据库初始化 | 约 1ms | 约 1ms |
| SDL / 渲染窗口初始化 | 353–417ms | 396–435ms |
| 皮肤、脚本、字体及音频初始化 | 128–144ms | 138–144ms |
| main 到场景对象初始化完成（累计） | 4107–4110ms | 785–833ms |

资源准备耗时降低约 93%，上述启动初始化累计减少约 3.3 秒。优化版刚安装后的另一次启动为资源准备 236ms、累计 810ms，结果一致。

以上区间不包含系统启动进程、进入 `main()` 前的动态链接以及场景初始化完成后的首帧呈现，不能当作“点击图标到屏幕出图”的完整测量。模拟器结果也不能直接换算为真机节省时间。用户随后已确认真机开屏加速验证通过，补测情况见下文。

加载画面出现后，示例歌曲扫描只需约 3–6ms，随后有约 1 秒的既有渐变动画。这与用户描述的首屏前等待不同，本次未改动画。

验证包括模拟器 Release 构建和启动、标题画面显示；临时文件系统夹具验证首次复制、保留自定义配置/成绩/歌曲/皮肤、更新着色器、增加新内置资源以及删除子目录后的自动补齐。夹具在独立临时目录运行，不修改用户资料。

### 真机空目录全量复制补测（2026-09-13）

用户确认开屏加速修复已通过真机验证，并反馈“首次安装后开屏大概 700 多 ms”。这是用户报告的整体开屏耗时估计，未提供该次观察的计时方法或资源目录初始状态。

随后在 USB 连接的 iPad Pro 11 英寸（第 3 代，iPad13,4）/ iPadOS 27.0（24A435），使用当前优化代码的 ARM64 Release 构建独立计时。资源集为 13,522 个文件、2,336 个目录，总文件内容 1,440,911,622 字节（约 1.44 GB / 1.34 GiB）。

每轮启动创建一个此前不存在的应用临时子目录，以它代替 Documents 作为复制目标，执行同一套 `ios_prepare_filesystem()` 资源遍历与复制逻辑。先测空目录全量复制，再在同一进程中立即复测已有资源检查。未卸载应用，测试路径不读写原 Documents 中的歌曲、配置和成绩。

| 轮次 | 空目录全量复制 | 随后已有资源检查 | 首次 / 再次实际复制文件数 |
| --- | ---: | ---: | ---: |
| 1 | 5790.238ms | 623.821ms | 13,522 / 21 |
| 2 | 5550.140ms | 619.885ms | 13,522 / 21 |
| 3 | 5602.079ms | 624.835ms | 13,522 / 21 |

全量复制范围为 **5.55–5.79 秒**，已有资源检查为 **620–625ms**；再次复制的 21 个文件为每次启动都更新的着色器。每轮计时结束后逐字节核对全部 13,522 个文件内容和目录存在性，均通过，并删除该轮测试副本。

测量后已移除全部临时计时和校验代码，普通 Release 构建及签名校验通过；确认产物不含测试标记后，已覆盖安装回 iPad 并成功发起启动。

计时从创建目标根目录前开始，到资源循环、确保 Songs 目录存在及切换工作目录完成后结束，包括遍历、路径计算、存在性检查、目录创建和同步复制调用；不包括内容核对、清理、渲染初始化或首帧呈现，也未额外调用 `fsync` 测量强制落盘时间。

这是在真机空目录中模拟首次资源初始化，未执行卸载重装，也未清空系统文件缓存；临时目录的位置、缓存状态和资源集可能与实际首次开屏观察不同。已有资源检查紧接首次复制，属于缓存已热的同进程复测。不能将这组数据解释为全新安装后的完整冷启动耗时，也不能用用户约 700 多毫秒的反馈代表全量资源复制耗时。

## 风险与边界情况

正常资源布局下，本次优化风险较低，但存在以下行为差异：

- **资源文件被误换成同名文件夹**：例如用文件夹替换 `texture.png`，新代码的 `exists()` 检查会跳过该条目，错误可能延后到资源加载时出现。旧代码的 `copy_file(skip_existing)` 会在复制阶段报错。已用宿主机上的独立临时夹具确认这项差异；两种实现都不会自动修复这种类型冲突。
- **启动期间并发删除资源目录**：若通过 Files / Finder 在父目录已被遍历后删除它，新代码不再为每个文件重新创建父目录，后续复制可能失败。旧代码也不保证并发修改安全，但能补建一部分此时被删除的父目录。这是代码分析发现的风险，尚未实测；启动资源准备期间应避免同时移动或删除资源。
- **内置资源使用符号链接**：`lexically_relative()` 只计算路径字面关系，不解析链接指向，因此带符号链接的资源布局可能与旧版的目标路径不同。本次检查的打包资源没有符号链接；以后若引入链接，需要重新验证复制位置和目录遍历行为。

以下限制原本就存在，并非本次优化引入：首次安装仍需复制全部内置资源；已存在但损坏的非着色器文件不会自动修复，已有同名非着色器资源也不会随升级覆盖，以保留用户修改。着色器仍会覆盖更新。缺失文件与“存在但损坏或类型错误”的文件应分开排查。

仍需补测其他 iPhone / iPad 的首屏等待与首次资源初始化、覆盖升级后的配置/成绩/自定义资源保留，以及低存储空间或复制中断后的恢复。上述真机空目录复制测试不能替代全新安装后的端到端首帧测量或这些场景的验证。

## 如何复建临时计时

最终代码不保留启动统计。需要复查时，临时使用 `std::chrono::steady_clock` 和 stderr 记录：

- `main()` 入口、`set_working_directory_to_executable()` 返回、`InitWindow()` 前后、`load_skin()` 返回、网络同步结束、`populate_screens()` 返回。
- `load_skin()` 内配置、全局纹理、脚本、字体和音频设备初始化各自的结束时间。
- `LoadingScreen` 扫描开始、`loading_complete` 置位和渐变完成时间。若要测首帧，还需单独记录首次 `EndDrawing()`，并结合外部录屏区分 CPU 提交与屏幕呈现。

用 `./build_ios.sh simulator` 构建，`xcrun simctl install` 安装，`xcrun simctl launch --terminate-running-process --stdout=/tmp/startup.out --stderr=/tmp/startup.err <模拟器 UUID> com.yataidon.app` 重复启动。重定向路径位于模拟器的 `data/tmp`，不是宿主机 `/tmp`。对比时保持资源、配置、构建类型一致，区分首次安装、首次启动和资源已存在的重复启动；不要卸载应用来测量已有用户数据的启动场景。测量后移除计时代码并重新构建。

真机空目录复制计时的复建方法：

1. 在 `ios_prepare_filesystem()` 加入临时环境变量分支 `YATAIDON_COPY_BENCHMARK`。仅该分支将目标改为 `NSTemporaryDirectory()/yataidon-copy-benchmark-<UUID>`，先确认目标不存在，不清空或替换 Documents。
2. 用 `std::chrono::steady_clock` 包住上述完整资源准备阶段，只在阶段结束后向 stderr 输出毫秒数和文件、目录、实际复制计数；在同一目标上立即重复一次。计数依据 `copy_file()` 的返回值，计时中不逐文件打印或核对内容。
3. 两次计时结束后，核对全部源文件与目标文件的内容及目录存在性，另行统计资源总字节数。恢复原工作目录后删除本轮临时目录，输出校验和清理结果，并在进入游戏配置、数据库和网络初始化前退出。
4. 用现有 Xcode 真机工程、实际签名团队及 Bundle ID 构建 Release，覆盖安装以保留应用数据。通过 `xcrun devicectl device process launch --device <设备标识> --terminate-existing --console --environment-variables '{"YATAIDON_COPY_BENCHMARK":"1"}' <实际 Bundle ID>` 收集日志，每轮重新启动生成全新目录，重复三轮。测量不需要附加调试器。
5. 保存数值与测试条件后移除临时分支、计时和校验代码，重新构建并覆盖安装普通 Release 版本。仓库不保留测试开关或诊断代码。
